# Security Policy

> This file describes how to report a vulnerability **in the Secure AI Code Library itself** — its registry, schemas, adapters, hook script, subagent runners, or documentation. For vulnerabilities in consumer projects that adopt this library, follow that project's own disclosure process.

## Supported versions

The library follows semantic versioning per [`SPEC.md`](./SPEC.md) §4.1.

| Version | Supported |
|---|---|
| `1.x.y` (Mythos-Aligned Foundation) | Yes — current. |
| Pre-`1.0.0` (this branch under development) | Best-effort during Phase 1–7 bring-up. |
| `0.x` v1 prompts-only fork | Not separately maintained; v2 carries the codebase forward. |

When a MAJOR version is released, the prior MAJOR receives security fixes for at least **90 days** from the release date.

## Reporting a vulnerability

**Please do not open a public issue for security vulnerabilities.**

Send a report to the upstream maintainer of `arvindiyu/SecureAICodeLibrary` via one of:

1. **GitHub Security Advisories** — preferred. Open a private advisory on the repository's Security tab. This is the canonical channel.
2. **Email** — if GitHub Security Advisories is unavailable, contact the repository owner directly via the email listed on the upstream GitHub profile.

### What to include

A useful report contains:

- **Affected version** (commit SHA, tag, or branch).
- **Component** — one of: `registry/rules/<id>`, `registry/subagents/<id>`, `registry/schemas/`, `adapters/<ide>`, `hooks/pre-commit.sh`, `docs/`, `index.html` / `js/` / `css/`.
- **Vulnerability class** — pick the closest: schema-bypass, rule-bypass, hook-bypass, citation-poisoning, prompt-injection-against-adapter, supply-chain (workflow / runner), token-budget DoS, audit-log tampering.
- **Reproducer** — minimal steps and a sample input.
- **Impact statement** — what does an attacker gain? What consumer projects are affected?
- **Suggested fix** (optional) — schema change, rule update, adapter patch.
- **Disclosure timeline preference** — default is the policy in the next section.

### What to expect

- **Acknowledgement** within 5 business days.
- **Triage decision** within 10 business days (accept / decline-with-rationale / request-more-info).
- **Fix or mitigation plan** within 30 days for HIGH/CRITICAL; 90 days for MEDIUM; backlog for LOW.
- **Coordinated disclosure** — we will work with the reporter on a disclosure date. Default is 90 days from triage acceptance, or earlier if a patch is available and CVEs are assigned.
- **Credit** — reporters are credited in `CHANGELOG.md` (under the released version) unless anonymity is requested.

### Severity classification

We use the same C / H / M / L scheme as the library itself (see [`docs/MANTHAN-CONTRACT.md`](./docs/MANTHAN-CONTRACT.md) when populated). For the **library artefact** (not consumer projects), severity is determined by:

| Severity | Definition |
|---|---|
| **CRITICAL** | Any defect that causes the pre-commit hook to silently pass a rule it should block, or that causes an adapter to write content that bypasses the always-on Tier 0 rules. Also: any audit-log defect that loses a record an investigator would need. |
| **HIGH** | A rule that misclassifies a known-bad pattern as safe; a schema flaw that allows malformed YAML to lower into the IDE; an adapter that ships full rule content into always-on context (token-cost blowup). |
| **MEDIUM** | A documentation citation that fails source hygiene but is technically truthful; a non-blocking lint that misfires. |
| **LOW** | A typo, broken link, or non-security cosmetic issue. |

## Out of scope for this policy

- Vulnerabilities in **Manthan** (<https://github.com/arvindiyu/manthan>) — report there.
- Vulnerabilities in third-party scanners invoked by Manthan — report to their maintainers.
- Vulnerabilities in IDEs (Cursor, GitHub Copilot, Claude Code, Windsurf) or the OS shell — report to the vendor.
- Vulnerabilities in consumer projects that adopt this library — report to that project's own contact.
- Theoretical token-cost concerns that do not bypass a control — open a normal issue.

## Supply chain

The library's own supply chain posture:

- Source of record: this repository's `main` branch.
- SBOM: [`sbom.cdx.json`](./sbom.cdx.json) (CycloneDX 1.5). Regenerated by `make sbom`. CI re-checks freshness (Phase 6).
- Pinning: consumers should pin to a tag (`v1.0.0`) or commit SHA, not `main`.
- Dependencies: the library ships only YAML, JSON Schema, Markdown, POSIX shell, and static HTML / JS / CSS. No runtime package dependencies. Build-time tooling (`tiktoken`, `yq`, `jq`, `rg`, `syft`) is declared in the Makefile and CI workflows.

## Trust model

See [`THREAT_MODEL.md`](./THREAT_MODEL.md) for the full STRIDE model. Briefly:

- **The maintainer is trusted** to merge rules that accurately reflect the cited standards. Reviewer discipline is the primary control.
- **The CI is trusted** to run `registry-ci.yml` + `source-hygiene.yml` on every PR.
- **Consumers** are responsible for pinning to a tag, running `merge-gate.yml`, and configuring `severity_threshold` appropriately for their context.
